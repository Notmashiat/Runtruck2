# 13 — Document System

Load paperwork: the checklist slots, the uploaded files, object storage, upload rules and permissions (architecture §21). Rank 6 (domain specification); the endpoints are in [api/documents.md](api/documents.md) and the tables in [03 §5.7](03-database.md).

Driver qualification documents (CDL, medical card…) are a different thing: `driver_documents` rows without files, owned by Safety ([03 §5.11.2](03-database.md), `docs/api/safety.md`).

---

## 1. Model

| concept | table | notes |
|---|---|---|
| **Slot** — one line of a load's "Documents" card | `documents` | `(load_id, document_type)` unique; `position` orders the card; `status` `pending` → `attached`; `attached_at` set with the first file |
| **Version** — one uploaded file | `document_versions` | append-only; `version_number` 1, 2, … per slot, the highest is current; `file_name`, `mime_type`, `size_bytes`, `checksum_sha256`, `uploaded_by_user_id`, `uploaded_at`, `storage_key` |
| **Object** — the bytes | S3-compatible bucket | never in PostgreSQL (architecture §21) |

Document types (`document_type`, Runtruck1 `DOCUMENTS` order): `rate_confirmation` "Rate confirmation" · `customer_load_tender` "Customer load tender" · `bill_of_lading` "Bill of lading" · `proof_of_delivery` "Proof of delivery" · `lumper_receipt` "Lumper receipt". Status chips: Attached (green), Pending (amber); on Accounting › Uninvoiced an attached POD reads "Attached", anything else "Missing" (03 §5.7.1).

### 1.1 Checklists

| load | slots (position: type) | source |
|---|---|---|
| created with New Load | 1 rate_confirmation, 2 customer_load_tender, 3 bill_of_lading, 4 proof_of_delivery, 5 lumper_receipt — all `pending` at creation, then `attached` as the files the user chose are uploaded | `POST /loads` then `POST /loads/:id/documents` per file |
| the 8 seeded board loads | 1 rate_confirmation, 2 bill_of_lading, 3 proof_of_delivery (Runtruck1 `LoadDetailPage.tsx:40-44`) | seed (03 §7.12) |
| the 11 seeded uninvoiced loads | 1 proof_of_delivery | seed (03 §7.13) |
| the 12 invoice-only loads | none | seed (03 §7.14) |

An upload for a type the load has no slot for creates the slot at `max(position) + 1`.

## 2. Object storage

| setting | value |
|---|---|
| Protocol | the plain S3 API only (replaceable provider, architecture §25) |
| Local / CI | SeaweedFS 4.48 from `infrastructure/docker/docker-compose.yml` (01 §6 C2); buckets created by `s3-init` |
| Bucket | `S3_BUCKET` (`runtruck-documents`; the integration tests use their own bucket) — private, no public ACL, no website hosting |
| Configuration | `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE` (`.env.example`); secrets only from the environment (architecture §34) |
| Object key | `org/{organization_id}/loads/{load_id}/documents/{version_id}` (03 §5.7.2), where `version_id` is the new version row's id, generated by the API **before** the upload transaction. Unique across the bucket (`document_versions_storage_key_uq`). Every part is known before any row is locked (§4.4), and the key carries no user-supplied text. |
| Object metadata | `Content-Type` = the detected type (§4.2); nothing else user-supplied |
| Client library | `@aws-sdk/client-s3` in `apps/api` (and in `packages/database` for the seed's placeholder objects, §7). Dependency check (architecture §40): needed for SigV4-signed S3 calls; no existing dependency speaks S3; maintained by AWS; Apache-2.0; a library, not a service. **Not added yet** — it is added with the documents module. |
| Client limits | `maxAttempts: 2`; connection timeout **5 s** and request (socket) timeout **60 s** (`NodeHttpHandler({ connectionTimeout: 5_000, requestTimeout: 60_000 })`); the upload's `PutObject` also gets an `AbortSignal.timeout(120_000)`. A timeout or any storage error maps to 502 `DEPENDENCY_UNAVAILABLE`. No storage call is ever made while a database transaction or row lock is held (§4.4), so a slow or hanging store cannot pin pooled connections or row locks. |

The API wraps the client in one `ObjectStorage` service (`put(key, bytes, contentType, checksum)`, `get(key)`, `head(key)`), so the provider stays replaceable and tests can point it at the test bucket.

## 3. Permissions

| action | permission | notes |
|---|---|---|
| See a load's slots and file names (load detail "Documents", `GET /loads/:id/documents`) | `documents.view` | on the load detail the list is omitted (`documents: null`) without it, and the web hides the card (07 §8 item 1) |
| Upload a file (`POST /loads/:id/documents`) | `documents.upload` | the load must be in the caller's organization, board or archived |
| Download a file (`GET /loads/:id/documents/:documentId/file`) | `documents.view` | specified, not built (§6) |

Tenant isolation: every lookup filters by `ctx.organizationId`; the slot's composite FK to the load and the version's composite FK to the slot keep rows inside one organization (03 §1.3); the object key starts with the organization id, and objects are only ever read through a version row found in the caller's organization.

## 4. Upload rules

### 4.1 Size and shape

- `multipart/form-data` with exactly one file part named `file` and one text field `documentType` (`uploadLoadDocumentSchema`). Extra files or fields are refused.
- Largest file **25 MiB** (`LOAD_DOCUMENT_MAX_BYTES`), enforced while the body streams (multer `limits.fileSize`, `files: 1`, `fields: 1`, `fieldSize: 1 KiB`); an empty file is refused. The body is held in memory (at most 25 MiB per request) and never written to local disk.
- The web origin proxies `/api/v1/*` to the API (04 §1). The Next rewrite streams the body; this path is outside the Next proxy matcher, so the proxy's body-size limit does not apply. Verify with a 25 MiB upload in the end-to-end suite.

### 4.2 Type allowlist (security)

Runtruck1's input says `accept=".pdf,image/*"`. The accept attribute is only a hint in the browser, so the server decides, from the file's **leading bytes** (the client's `Content-Type` and extension are ignored):

| detected | signature |
|---|---|
| `application/pdf` | `%PDF-` |
| `image/jpeg` | `FF D8 FF` |
| `image/png` | `89 50 4E 47 0D 0A 1A 0A` |
| `image/gif` | `GIF87a` / `GIF89a` |
| `image/webp` | `RIFF????WEBP` |
| `image/tiff` | `49 49 2A 00` / `4D 4D 00 2A` |
| `image/bmp` | `BM`, **and** a well-formed header: length ≥ 26; the little-endian file size at bytes 2–5 equals the upload size; the DIB header size at bytes 14–17 is one of 12, 40, 52, 56, 108, 124. A file that merely starts with `BM` (e.g. `BM<html><script>…`) is refused. |
| `image/heic`, `image/heif`, `image/avif` | ISO-BMFF `ftyp` box with brand `heic`/`heix`/`hevc`/`hevx` → heic, `mif1`/`msf1` → heif, `avif`/`avis` → avif |

Anything else — including **SVG** (an `image/*` type that can carry script), HTML, archives and executables — is refused with 400 `DOCUMENT_FILE_TYPE_NOT_ALLOWED` ("Attach a PDF or an image."). This is the one place the server refuses something Runtruck1's picker could select; it is a security rule (D6 does not weaken server checks). The detection is a small pure function in the documents module with a unit test per signature, including the refusals `BM<html>…` (a two-byte match without a valid BMP header), `<svg …>`, `<!DOCTYPE html>` and an empty file; no dependency.

### 4.3 File name

The stored `file_name` is the uploaded name with any path removed (last segment after `/` or `\`), control characters and `"` removed, Unicode NFC-normalized, trimmed, and cut to 255 characters; if nothing is left it becomes `document`. It is display data only: it never reaches the object key, a header or a file system path unescaped.

### 4.4 Upload order and failure handling

The object is written **before** the database transaction, so a slow or hanging object store never holds a pooled connection or a row lock (§2 client limits):

1. Read and check the file (§4.1–§4.3: size, detected type, name) and compute its SHA-256. Nothing touches the database yet.
2. Find the load in the caller's organization (`SELECT id FROM loads WHERE organization_id = $1 AND id = $2`, no lock); 404 `LOAD_NOT_FOUND` otherwise.
3. Generate the version id (`randomUUID()`) and build `storage_key` per §2 from the organization, the load and that id.
4. **Put the object** (with `Content-Type` and the SHA-256 checksum header), outside any transaction. If storage fails or times out, answer 502 `DEPENDENCY_UNAVAILABLE` ("Document storage is unavailable. Try again."); nothing is recorded.
5. Open **one database transaction** (04 §7):
   1. Insert the slot if the load has none of this type (`ON CONFLICT (organization_id, load_id, document_type) DO NOTHING`), then lock it (`SELECT … FOR UPDATE`) so concurrent uploads to one slot get consecutive version numbers.
   2. `version_number` = current highest + 1. Insert the version with the id of step 3 and its `storage_key`; set the slot `attached` and `attached_at = coalesce(attached_at, now)`; `uploaded_at` = `ClockService.now()` (business "now", D4).
   3. If the slot is `proof_of_delivery`, the load is `needs_pod` **and** `hasPermissions(ctx.permissions, ['loads.update'])`, move the load to `delivered` ([08](08-load-lifecycle.md) T12). Without `loads.update` the file is attached and the status is left unchanged (no status audit or event).
   4. Audit and events (§5). Commit.
6. If the transaction fails after the object was written, the object is an orphan: harmless (no row points at it, and its key contains a version id that no row will ever reuse). The periodic cleanup job that deletes keys without a version row (§6) removes it.

## 5. Audit, events, activity

| when | audit action (`entity_type` `document`, label "L-40223 · Rate confirmation") | events |
|---|---|---|
| a file is uploaded | `DOCUMENT_UPLOADED` `next: {loadId, documentType, versionNumber, fileName, mimeType, sizeBytes, checksumSha256}` | `DocumentUploaded` (aggregate `document`) `{loadId, documentId, documentVersionId, documentType, versionNumber}`; plus `PODUploaded` (aggregate `document`) `{loadId, documentId, documentVersionId}` for `proof_of_delivery` (architecture §23) |
| the POD moves the load to delivered (T12, only with `loads.update`) | `LOAD_STATUS_CHANGED` (entity `load`, `previous: {status: 'needs_pod'}`, `next: {status: 'delivered'}`) | `LoadStatusChanged` (aggregate `load`) `{loadId, loadNumber, from: 'needs_pod', to: 'delivered'}` |

Payload names and aggregates are registered in [17 §5](17-event-architecture.md).

No `load_activity` row is written for an upload: Runtruck1's created loads show only "Load created by …" and "Driver instructions: …" in Activity even with files attached (D6). The seeded "Bill of lading uploaded from the cab" rows are seed data (D7), written as they are.

Future consumers (none in this release): a `document-processing` job (architecture §24) for thumbnails, OCR and AI extraction subscribes to `DocumentUploaded`.

## 6. Not implemented in this release (tracked)

- **Download** `GET /loads/:id/documents/:documentId/file[?version=n]` (`documents.view`): no Runtruck1 screen opens a file. Contract when built: the API streams the object (no presigned URL, so permission checks and the bucket stay private) with `Content-Type` = stored type, `Content-Disposition: attachment; filename*=UTF-8''<file name>`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`.
- Upload control on the load detail page (Runtruck1 has none).
- Deleting a version or a slot (documents are business records; replacing a file adds a version).
- Malware scanning, retention rules, thumbnails, OCR.
- **Orphan-object cleanup**: a repeatable job ([18](18-background-jobs.md)) that lists `org/{organization_id}/loads/…/documents/` keys older than a day with no `document_versions` row and deletes them (uploads whose transaction failed, §4.4 step 6).
- Direct-to-bucket (presigned) uploads.

## 7. Seeded documents

The seed writes the slots of §1.1 and, for every attached slot, one version row for a fixed placeholder PDF (`PLACEHOLDER_PDF`: `mime_type` `application/pdf`, size and SHA-256 of those bytes, `uploaded_by_user_id` null, `uploaded_at` = `attached_at` = 2026-09-03 10:05 organization time, key per §2). File names: `rate-confirmation-L-<n>.pdf`, `bill-of-lading-L-<n>.pdf`, `proof-of-delivery-L-<n>.pdf`.

**Status: metadata only — the placeholder objects are not written yet** (design brief §3 requires them; tracked, not done). `packages/database` has no S3 client, so all 21 seeded versions (and the Test Carrier Co fixture's one) point at missing objects; a download, integrity check or cleanup job would fail on them. Required when `@aws-sdk/client-s3` is added to `packages/database` (§2): after the seed transaction commits, `pnpm db:seed`, `pnpm db:reset` and the test and e2e fixture seeding (`seedTestFixtures`, including `testing/other-organization.ts`) `PutObject` `PLACEHOLDER_PDF` (`ContentType: application/pdf`) at every seeded `storage_key` in `S3_BUCKET` (`runtruck-documents`; `runtruck-documents-test` for tests and e2e), idempotently (overwrite); an integration test `HeadObject`s every seeded key. Until then, the cleanup job of §6 must not run against seeded keys.

## 8. Decisions to record (01 §6)

- The server accepts only PDFs and the raster image types of §4.2 (detected from bytes), at most 25 MiB, one file per request. SVG and every non-image type are refused although Runtruck1's picker could select them (security).
- New Load uploads the chosen files after the load is created, one request per file; a failed upload leaves that slot Pending and does not undo the load ([api/documents.md §5](api/documents.md)).
- Uploads write no `load_activity` row (D6 parity).
- `@aws-sdk/client-s3` is the S3 client (dependency check §2), with the limits of §2; the object is written before the database transaction (§4.4), under a key built from a pre-generated version id.
- A proof-of-delivery upload changes the load's status only when the uploader also holds `loads.update` (08 T12).
- BMP is accepted only with a well-formed header (§4.2).
